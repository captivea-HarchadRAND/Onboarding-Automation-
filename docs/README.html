Onboarding Automation

Application interne de gestion des arrivées et départs de collaborateurs. Elle automatise la création de comptes Microsoft 365, l'attribution de licences, l'ajout aux groupes SharePoint, Teams, Exchange et GitHub — le tout piloté depuis une interface web sans intervention technique.

Node.js + Express React + Vite Microsoft Graph API Exchange Online PS Déployé sur VPS OVH SQLite (sql.js)

Vue d'ensemble

L'application est utilisée par des opérateurs RH ou IT pour déclencher un onboarding complet en quelques clics. Elle est organisée autour de deux flux principaux :

Onboarding
Création du compte Azure AD, assignation d'une licence Microsoft 365, ajout aux groupes configurés (SharePoint, Teams, Exchange, GitHub). Les credentials sont affichés immédiatement après la création du compte.
Offboarding
Désactivation du compte AD, révocation des sessions, retrait de tous les groupes, transfert optionnel des emails et des accès OneDrive, retrait de la licence. Déclenchable uniquement par un admin.

Architecture

L'application est un monorepo avec un backend Express et un frontend React compilé statiquement. En production, Nginx sert le frontend buildé et proxifie l'API vers le backend Node.js géré par PM2.

# Flux de données simplifié

Navigateur
  └─→ Nginx (:443)
        ├─→ /api/*  →  PM2: node backend/server.js (:8081)
        │                    ├─→ Microsoft Graph API (Azure AD)
        │                    ├─→ pwsh /opt/scripts/exchange.ps1
        │                    └─→ SQLite (sql.js, fichier .db)
        └─→ /*      →  dist/ (build Vite, servi statiquement)
⚠️
Le backend utilise sql.js (SQLite en mémoire, persisté sur disque via fs.writeFileSync). La base est chargée au démarrage et sauvegardée après chaque écriture. En cas de crash, les données non encore sauvegardées peuvent être perdues — prévoir un backup régulier du fichier .db.

Prérequis

Côté serveur (VPS / machine de déploiement)

  • Node.js ≥ 20 LTS
  • PM2 (npm i -g pm2)
  • PowerShell 7+ (pwsh) avec le module ExchangeOnlineManagement
  • Nginx
  • Git

Côté Azure

  • Une App Registration Azure AD avec les permissions Microsoft Graph suivantes (Application, pas Delegated) : User.ReadWrite.All, Group.ReadWrite.All, Directory.ReadWrite.All, TeamMember.ReadWrite.All
  • Un client secret généré pour cette app (ou un certificat)
  • Le Tenant ID et Client ID de l'app

Pour Exchange Online (distribution lists)

  • Un certificat .pfx déposé dans /opt/exchange.pfx (chmod 600)
  • L'App Registration doit avoir le rôle Exchange App Policy via PowerShell (New-ServicePrincipal)
  • Le script /opt/scripts/exchange.ps1 (chmod 500)

MOCK_FAIL_STEP=2   # 1=création compte, 2=groupe, 3=licence

Pipeline onboarding

Le pipeline est découpé en deux phases qui tournent de manière asynchrone. L'opérateur reçoit les credentials dès la fin de la Phase 1, sans attendre l'intégration complète aux groupes.

Phase 1 — Synchrone (compte visible immédiatement)

1
Création du compte Azure AD
Appel POST /users via Graph API. Le mot de passe temporaire est généré par Azure et stocké en mémoire dans tempPasswordStore. Le compte AD ID est sauvegardé en base pour le rollback.
2
Ajout au groupe principal
Ajout au groupe M365 sélectionné par l'opérateur lors du wizard (ex: équipe département). Configurable et désactivable via le schéma dans Admin.
3
Assignation de la licence Microsoft 365
Appel POST /users/{id}/assignLicense. Exchange Online prend 1 à 5 minutes à se provisionner après la création du compte AD — le backend retente automatiquement jusqu'à 5 fois avec délais croissants (15s, 30s, 45s, 60s, 90s) sur les erreurs Exchange-not-ready.
✅
À la fin de la Phase 1, le statut passe à partial. Le frontend arrête son polling et affiche immédiatement les credentials (email + mot de passe temporaire). Le mot de passe n'est renvoyé qu'une seule fois — il est supprimé du store en mémoire après la première lecture.

Phase 2 — Background (60 secondes après Phase 1)

La Phase 2 est lancée avec setTimeout(60 000) pour laisser à Microsoft le temps de provisionner la boîte Exchange avant d'ajouter l'utilisateur aux groupes de messagerie.

4
Ajout aux groupes SharePoint & Communication
Groupes globaux, groupes par pays, groupes par ville, groupes de communication (par département/rôle). Pour les distribution lists et shared mailboxes, Exchange PowerShell est utilisé en fallback automatique si Graph API refuse (Add-DistributionGroupMember).
5
Invitation GitHub
Si GITHUB_TOKEN est configuré : invitation à l'organisation via POST /orgs/{org}/invitations, puis ajout au team all via PUT /orgs/{org}/teams/{slug}/memberships/{email}.
6
Ajout au canal Microsoft Teams
Si un channelId est configuré pour la ville de l'employé : ajout via POST /teams/{teamsId}/channels/{channelId}/members. Le teamsId est le Group Object ID du groupe pays.

Rollback automatique

Si la Phase 1 échoue (avant que le statut passe à partial), le compte Azure AD est supprimé automatiquement (DELETE /users/{id}). La Phase 2 ne déclenche jamais de rollback — les erreurs d'ajout aux groupes sont loguées mais n'affectent pas le compte déjà créé.

Traitement background — points d'attention

Deux fonctions clés dans server.js :

  • executeOnboarding(id) — Phase 1. Appelée juste après la création de l'enregistrement en base. Si elle échoue avant partial, rollback. Si elle réussit, programme la Phase 2.
  • executeOnboardingBackground(id, adUserId, userPrincipalName, step4Enabled) — Phase 2. Tournée 60s plus tard. Toutes les erreurs sont rattrapées et loguées, le statut final passe à done même si des sous-étapes échouent.
🔴
Le backend utilise setTimeout pour la Phase 2. Si PM2 redémarre le process pendant les 60 secondes d'attente, la Phase 2 ne s'exécutera pas. L'onboarding restera en statut partial indéfiniment. Vérifier les logs PM2 si un onboarding ne passe pas à done.

Offboarding

Accessible uniquement aux administrateurs. Déclenche les actions suivantes dans l'ordre :

  1. Recherche du compte par email via GET /users/{email}
  2. Désactivation du compte (accountEnabled: false)
  3. Révocation de toutes les sessions actives (revokeSignInSessions)
  4. Retrait de tous les groupes M365 auxquels l'utilisateur appartient
  5. Transfert optionnel des emails (règle de redirection Outlook)
  6. Transfert optionnel des accès OneDrive
  7. Retrait de toutes les licences
⚠️
L'offboarding génère un script PowerShell téléchargeable pour les actions manuelles complémentaires (ex: retirer d'une distribution list Exchange). Le compte AD n'est pas supprimé — il est désactivé et conservé.

Configuration admin (no-code)

Toute la configuration métier se fait via Admin → Paramètres. Les données sont stockées dans la table settings de la base SQLite (clé/valeur JSON).

Groupes globaux

Groupes M365 ajoutés à tous les nouveaux employés quel que soit leur pays ou département. Champ id = Group Object ID Azure AD.

Groupes par pays / ville

Chaque entrée correspond à un pays (ex: France). Elle contient :

  • id — Group Object ID Azure AD et Teams Group ID (même valeur)
  • location — code pays utilisé dans le wizard
  • cities[] — liste de villes, chacune avec son propre id (Group Object ID) et channelId (Teams Channel ID, optionnel)

Groupes de communication (distribution lists / shared mailboxes)

Groupes assignés par département et/ou localisation. Champ supplémentaire exchangeEmail pour les distribution lists Exchange (ex: sales@captivea.com). Si ce champ est présent, Exchange PowerShell sera utilisé automatiquement en cas d'échec Graph API.

Schéma d'onboarding

Chaque étape peut être activée ou désactivée individuellement via Admin → Schéma. Permet de désactiver temporairement une intégration sans modifier le code.

Sessions

Cookie httpOnly + sameSite: strict + secure (en production). Durée : 14 jours. Stockées dans la table sessions.

2FA

Si SMTP est configuré, un code OTP à 6 chiffres est envoyé par email à chaque connexion. Le code expire après 10 minutes. Limité à 5 tentatives avant blocage.

Rate limiting

Toutes les routes d'authentification sont protégées par express-rate-limit : 10 tentatives maximum par fenêtre de 15 minutes.

Invitations

Les nouveaux comptes opérateurs sont créés par un admin via Admin → Utilisateurs. Un lien d'invitation avec token UUID est généré — le destinataire définit son propre mot de passe via ce lien.

Exchange Online PowerShell

Utilisé pour ajouter des utilisateurs aux distribution lists et configurer les shared mailboxes (opérations refusées par Graph API).

Installation sur le VPS

# Installer le module Exchange Online
pwsh -Command "Install-Module ExchangeOnlineManagement -Force -Scope AllUsers"

# Déposer le certificat
cp exchange.pfx /opt/exchange.pfx
chmod 600 /opt/exchange.pfx

# Déposer le script
cp exchange.ps1 /opt/scripts/exchange.ps1
chmod 500 /opt/scripts/exchange.ps1

Actions disponibles

ActionDescription
AddDistributionMemberAjoute un utilisateur à une distribution list via Add-DistributionGroupMember. Identity = email de la liste (ex: sales@captivea.com)

⚠️
Toutes les valeurs passées à runExchangeScript() sont validées (whitelist d'actions, regex email/GUID). Le processus est lancé via spawn() avec un tableau d'arguments — pas de shell string — ce qui rend toute injection de commande impossible.

GitHub

Si GITHUB_TOKEN est défini dans .env, chaque onboarding invite automatiquement l'employé dans l'organisation GitHub et l'ajoute au team all.

⚠️
L'invitation GitHub est envoyée à l'adresse email M365 du nouvel employé. Si la boîte Exchange n'est pas encore provisionnée, l'email d'invitation peut ne pas être reçu immédiatement — c'est pour cette raison que la Phase 2 attend 60 secondes après l'assignation de la licence.

Le token GitHub doit avoir le scope admin:org. Pour le consulter ou le régénérer : GitHub → Settings → Developer settings → Personal access tokens.

Microsoft Teams

L'ajout au canal Teams est conditionnel : il ne se produit que si un channelId est configuré pour la ville de l'employé dans Admin → Groupes par pays.

Comment récupérer les IDs

# Depuis une URL Teams :
https://teams.microsoft.com/l/channel/{channelId}/...?groupId={teamsGroupId}

# teamsGroupId == Group Object ID du groupe pays (même valeur que le champ "id")
# channelId = la portion encodée après /channel/ dans l'URL

CI/CD — GitHub Actions

À chaque push sur main, le workflow .github/workflows/deploy.yml déploie automatiquement sur le VPS via SSH.

# Ce qui s'exécute sur le VPS à chaque deploy
cd /var/www/onboarding
git pull origin main
cd frontend && npm install && npm run build   # rebuild obligatoire
cd ../backend && npm install --production
pm2 restart onboarding
🔴
Le fichier backend/.env n'est jamais touché par le CI/CD. Il vit uniquement sur le VPS. Ne jamais le commiter dans le repo. Ne jamais l'ajouter aux secrets GitHub pour l'envoyer automatiquement.

Secret GitHub requis

Dans GitHub → Settings → Secrets → Actions, ajouter : SSH_PRIVATE_KEY (clé privée SSH pour accéder au VPS, port 2215).

Configuration serveur

  • SSH sur le port 2215 (pas le port standard 22)
  • fail2ban configuré sur le port 2215 — max 3 tentatives / 5 min, ban 30 min
  • UFW : seuls les ports 80, 443, 2215 sont ouverts

Sécurité — points clés

Pas de secrets dans le code
Toutes les clés (Azure, Exchange, GitHub, SMTP) sont dans .env uniquement. Le frontend ne contient aucun secret.
Contrôle d'accès serveur
Chaque route API est protégée par auth et/ou requireRole('admin'). Un opérateur ne peut accéder qu'à ses propres onboardings.
Anti-injection
Requêtes SQL paramétrées, OData filtré par whitelist de caractères, Exchange via spawn() avec tableau d'args, escapeHtml() dans les emails.
Mot de passe temporaire
Jamais stocké en base. En mémoire uniquement (tempPasswordStore), retourné une seule fois via l'API, détruit immédiatement après lecture. Expire au bout de 10 minutes.
